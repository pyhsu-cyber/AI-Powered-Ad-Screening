## 0. 系統定位與範圍

### 0.1 目的

協助一般民眾與稽核人員，把「看到一則疑似違規的健康食品／化粧品廣告」到「送出一封格式正確、
法條引用正確的檢舉陳情信」這段流程，從人工查法規壓縮到數分鐘內完成。

### 0.2 定位

**初篩工具（Screening Tool）**，不是裁決系統。命中結果一律需人工複核，
最終違規認定以主管機關為準。此定位決定了兩件設計取捨：

1. **召回率優先於精確率**——寧可多列一項待人工排除，不可漏掉違規句。
2. **所有自動判定結果都必須可被使用者修改**——OCR 文字、產品名稱、產品類別皆可編輯。

### 0.3 範圍內

- 食品、健康食品、化粧品、藥品、醫療器材五類廣告的違規用語快篩
- 圖片文字辨識（OCR）與文字直接輸入
- 違規用語比對、法條與罰則對應
- 衛生局陳情信生成、列印與 PDF 輸出

### 0.4 範圍外（本版不做）

- 自動送件至各縣市衛生局線上陳情系統（見 OQ02）
- 多人協作、案件管理、檢舉進度追蹤（見 OQ04）
- 廣告來源自動擷取（給網址自動抓圖文）
- 影片、音訊廣告

### 0.5 名詞定義

| 名詞 | 定義 |
|---|---|
| 免費模式 | 不需任何 API 金鑰，以 OCR + 關鍵字比對運作的預設模式 |
| AI 模式 | 設定 API 金鑰後，由多模態模型直接判讀圖片語意的模式 |
| 宣稱醫療效能 | 違規分類之一，對應食安法 28-2 等療效禁止條文 |
| 誇大不實 | 違規分類之一，對應食安法 28-1 等誇大禁止條文 |
| 死鍵字 | 因被較短關鍵字遮蔽、或與實際文字不符，而永遠不會被觸發的關鍵字 |
| 交叉比對 | 分析完成後自動以第二套 OCR 引擎重讀並合併結果的機制 |

### 0.6 現況標記說明

每條 FR 標註對照程式 v5 的狀態：`已實作` / `部分完成` / `未實作`。
完整缺口分析另見 `docs/spec_v1_gap_analysis.md`（本文不重複）。

## 1. Functional Requirements（功能需求）

### FR01 廣告素材輸入　`已實作`

- 支援三種輸入方式，皆進入同一條處理管線：
  1. 點擊上傳區開啟檔案選擇器
  2. 拖曳圖片檔至上傳區（`dragover` / `drop`）
  3. 於頁面任意處按 `Ctrl + V` 貼上剪貼簿圖片（監聽 `document` 的 `paste`，
     僅在 `clipboardData.items` 含 `image/*` 時攔截，否則不干擾文字貼上）
- 接受格式：`image/png`、`image/jpeg`、`image/webp`、`image/gif`、`image/bmp`
- 單檔上限 **10 MB**（常數 `MAX_MB`）
- 亦支援完全不上傳圖片，直接於「廣告文字」欄位貼上文案
- 載入成功後於上傳區顯示：檔名、格式、像素尺寸、檔案大小

### FR02 圖片文字辨識（雙引擎）　`已實作`

系統提供兩套 OCR 引擎，預設「主引擎先出結果、備援引擎背景補漏」：

| 引擎 | 角色 | 實作 | 特性 |
|---|---|---|---|
| Windows 內建 OCR | 主引擎 | 後端 `subprocess` 呼叫 `ocr.ps1`，使用 `Windows.Media.Ocr` | 離線、約 1 秒、免下載 |
| tesseract.js | 備援＋交叉比對 | 前端瀏覽器內執行，模型自 CDN 載入 | 首次需下載約 9 MB，之後由瀏覽器快取 |

- **主引擎路徑**：`POST /api/analyze` 夾帶 `image_base64`，後端 OCR 後回傳 `ad_text` 與比對結果。
- **能力偵測**：前端以 `serverOcr` 三態旗標（`null` 未知 / `true` 可用 / `false` 不可用）記錄後端 OCR 能力。
  首次呼叫失敗即降級為 `false`，該工作階段後續直接走備援引擎。
- **交叉比對**：主引擎分析完成並渲染後，非同步啟動備援引擎重讀同一張圖，
  將新文字附加至既有文字後重新比對；**僅在違規項數增加時**才更新畫面並提示使用者。
- 交叉比對不得阻塞主結果呈現（不 `await`）。

### FR03 OCR 後處理與正規化　`已實作`

OCR 原始輸出不可直接送比對，須先經 `tidyCJK()` 正規化，處理順序固定：

1. **全形英數轉半形**（`０-９Ａ-Ｚａ-ｚ` → ASCII）——後端為純字串比對，
   `７天美白` 比對不到 `7天美白`，不轉換會直接漏抓。
2. 移除 `\r`、合併連續空白（含 ` `）
3. **還原 CJK 字間空白**：CJK 字元後接空白再接 CJK／英數者，移除該空白；
   英數後接空白再接 CJK 者亦同。英文詞間空白必須保留。
4. 收斂行尾空白與三行以上連續空行

> 實測依據：未經此步驟的 OCR 文字僅命中 1 個關鍵字，處理後命中 9 個。

### FR04 違規關鍵字比對引擎　`已實作`（沿用既有 exe）

- 比對方式：**純子字串比對**（`if 關鍵字 in 廣告文字`），無斷詞、無語意判斷。
- 關鍵字分兩類，儲存於 `regulations.json` 的 `demo_keywords`：
  - `medical_efficacy` — 宣稱醫療效能
  - `exaggeration` — 誇大不實
- 現況規模：醫療效能 168 個、誇大不實 170 個，合計 **338 個**。
- 引擎已實測特性（新增關鍵字時必須遵守，違反者見 EC07）：

| 特性 | 行為 |
|---|---|
| 重疊詞 | 清單同時有「治療」與「治療糖尿病」時，一句話會被算成**兩筆**違規 |
| 同詞跨兩類 | 同一詞放在兩個分類會被算成**兩筆** |
| 同詞重複出現 | 同一詞在文中出現多次只算一筆 |
| 英數大小寫 | 敏感（`PM2.5` 比對不到 `pm2.5`） |
| 資料載入時機 | `regulations.json` 於**程式啟動時載入一次**，修改後必須重啟 |

### FR05 法規資料庫與法條對應　`已實作`

- `regulations.json` 的 `laws` 陣列存放 **10 條**法規，每條含
  `id / law_name / article / summary / penalty / url`。
- 後端示範模式**一律回傳食安法**（寫死於 exe，無法修改），前端須依「產品類別」改寫：

| 產品類別 | 宣稱醫療效能 | 誇大不實 |
|---|---|---|
| 食品 | `fsa-28-2` 食安法 28-2 | `fsa-28-1` 食安法 28-1 |
| 健康食品 | `hf-14-2` | `hf-14-1` |
| 化粧品 | `cos-10-2` 化粧品法 10-2 | `cos-10-1` 化粧品法 10-1（4萬～20萬） |
| 藥品 | `pha-66` 藥事法 66 | `pha-66` |
| 醫療器材 | `md-41` 醫療器材管理法 41-1 | `md-41` |
| 其他／無法判定 | 沿用後端回傳值 | 沿用後端回傳值 |

- 藥品與醫療器材本得宣稱療效，違規點在「廣告未經核准或逾越核准範圍」，
  故兩類皆對應廣告核准條文，而非療效禁止條文。
- 備用法條：`pha-69`（非藥物不得宣稱醫療效能）、`md-46`（非醫療器材不得宣稱醫療效能），
  供 AI 模式在判定產品並非藥物／醫材時引用。
- 對應邏輯集中於 `lawFor(violation, productType)` 單一函式，
  違規清單與陳情信共用，切換產品類別須即時重繪。

### FR06 AI 語意分析模式（選用）　`部分完成`

免費模式僅能抓字面用語；暗示性表達（如「告別藥罐子」）需語意判讀。

- **Claude 模式**：於程式資料夾建立 `api_key.txt`（`sk-ant-` 開頭），重啟後由後端呼叫，
  圖片直送模型。`GET /api/status` 回傳 `ai_enabled` 供前端切換流程。
- **Gemini 免費模式**：金鑰存於瀏覽器 `localStorage`（鍵名 `gemini_key`），
  前端直接呼叫 `generativelanguage.googleapis.com`，依序嘗試
  `gemini-2.5-flash` → `gemini-2.0-flash` → `gemini-flash-latest`。
  回傳經 `normalizeAI()` 整形為與免費模式相同的資料結構，法條由 `LAWS` 表補齊。
  `狀態`：邏輯完整且有單元測試，但 v5 已移除設定 UI，目前僅能以 `localStorage` 手動啟用。
- AI 模式須明確告知使用者「圖片將傳送至外部服務」。

### FR07 快篩結果呈現　`已實作`

- 摘要列：產品名稱、產品類別、風險等級（`高` / `中` / `低` / `無明顯違規`，依等級著色）
- 違規清單，每項含：
  - 引用原句與違規分類標籤（醫療效能為紅、誇大不實為橘）
  - 違規理由
  - 引用法條全名、條次、條文摘要、罰則、全國法規資料庫連結
  - 判定信心程度
- 無違規時顯示明確的「未偵測到明顯違規字句」而非空白

### FR08 陳情信生成　`已實作`

- 依公文格式輸出：受文者、主旨、說明一～五、檢舉人、聯絡方式、陳情日期（民國年）
- 欄位：產品名稱（自動帶入，可改）、產品類別、受文機關（22 縣市衛生局下拉）、
  刊登平台、廣告網址、發現日期、檢舉人姓名、聯絡電話／Email
- 說明二逐條列出違規事實，每條含引用原句、分類、理由、涉違反法條與罰則
- 說明四自動計算檢附截圖份數
- 說明五的檢舉獎勵辦法名稱須依產品類別調整；
  非食品類不得引用「檢舉違反食品安全衛生管理法案件獎勵辦法」
- 產品名稱自動帶入規則：AI 模式取模型回傳值；免費模式取 OCR 文字第一行
  （長度 2～30 字才採用），欄位已有值時不覆蓋
- **發現日期預設為今天**（頁面載入時填入，可自行修改）。
  須以本地時間計算，不得使用 `toISOString()`——那是 UTC，台灣清晨時段會填成昨天

### FR09 輸出與交付　`已實作`

- **列印／存成 PDF**：`window.print()`，列印樣式僅保留陳情信本體，
  且必須強制白底黑字（畫面為深色主題，不可直接沿用）
- **複製全文**：`navigator.clipboard.writeText()`，
  失敗時（視窗失焦、權限不足）須顯示替代指引，不得靜默失敗

### FR10 關鍵字資料庫維護　`已實作`

- `regulations.json` 為純文字檔，使用者可用記事本增修
- 每個關鍵字的法規依據、來源與真實裁罰案例，記錄於 `說明文件/關鍵字來源.md`
- 維護規則須在說明文件中明示（避免死鍵字與誤判），至少涵蓋：
  不得收錄包含既有關鍵字的詞、一詞只能歸一類、不得收錄法規明文允許的宣稱用語、
  不得收錄過於通用的詞、**必須以裁處書原文測試而非改寫過的句子**

### FR11 系統模式判定與提示　`已實作`

- 啟動時以 `GET /api/status` 取得 `ai_enabled`，決定走 AI 或免費流程
- 流程進度以 STEP 1～4 指示器呈現，隨流程點亮
- 處理中須顯示步驟編號、目前動作與預估時間（例：「步驟 1／2　讀取圖片上的文字…」
  ／副標「Windows 內建 OCR 處理中，通常 1～2 秒」）

### FR12 使用者訊息與狀態回饋　`已實作`

- **所有訊息一律頁面內顯示，禁止使用 `alert()`**
- 三種樣式：錯誤（紅）／警告（黃）／成功（綠），可手動關閉，成功訊息自動淡出
- 處理中的按鈕須同時具備：停用、`cursor: not-allowed`、轉圈圖示、文字改為進行式，
  並鎖住同流程的其他按鈕以防重複觸發

### FR13 版本管理與封裝　`已實作`

- 每次修改進版，產出 `違規廣告快篩_v{N}.zip`，解開後資料夾名與版本一致
- `說明文件/版本紀錄.md` 記錄每版變更內容與驗證結果
- 前端原始碼拆為 `實作作業/{index.html, styles.css, app.js}`，
  以 `build.py` 合併內嵌產生實際執行的 `static/index.html`（原因見 NFR-A03）

## 2. Edge Cases（邊界與極端情境）

### EC01 Windows OCR 不可用（分支處理）

- 【缺中文 OCR 語言套件】：`ocr.ps1` 回傳空結果或錯誤 → 自動改用瀏覽器 OCR，
  並於狀態列說明改用原因。
- 【`ocr.ps1` 被防毒軟體攔截或刪除】：`subprocess` 失敗 → 同上降級。
  （實測：含 `HttpListener` 常駐服務的 PowerShell 腳本會被 AMSI 判為惡意並**直接刪檔**，
  故本系統採一次性 CLI 腳本設計）
- 【使用者執行的是不支援圖片的舊版 exe】：後端回「示範模式僅支援文字分析」→ 同上降級。
- 三種情形皆須將 `serverOcr` 設為 `false`，本工作階段不再重試主引擎。

### EC02 OCR 讀不到文字（分支處理）

- 【主引擎讀到字數 < 10】：不視為引擎故障（`serverOcr` 維持 `true`），
  直接改用備援引擎重讀該張圖。
- 【兩套引擎都讀不到】：不送出分析，顯示可操作的指引
  （手動貼上文案；或提示以 `Win + Shift + S` 截圖後用「剪取工具 → 文字動作」複製文字）。
- 【圖片極小（短邊 < 1000px）且字數 < 10】：備援引擎放大 2 倍重試一次，取字數較多者。

> 注意：不得無條件放大。實測 3 倍放大會使關鍵字命中從 8 降至 3——
> 插補會糊掉筆畫，反而降低辨識率。

### EC03 使用者修改辨識文字後重新分析

- 【文字框為空】：走 OCR 流程。
- 【文字框已有內容】：**直接以該內容比對，不得重跑 OCR**，否則會覆蓋使用者的修正。
- 交叉比對啟動前須確認文字框內容仍等於上次 OCR 結果（`lastOcrText`），
  使用者已編輯則放棄交叉比對。

### EC04 更換圖片時的狀態殘留

- 【文字框內容 == 上次 OCR 結果】：視為機器產生，清空以免污染新圖分析。
- 【文字框內容為使用者自行輸入】：保留。
- 產品名稱、產品類別等已填欄位一律保留，重繪結果時不得覆寫。

### EC05 輸入檔案異常（分支處理）

- 【非圖片格式】：擋下並明示實際 MIME 型別與可接受格式。
- 【超過 10 MB】：擋下並顯示實際大小與上限，建議裁切或壓縮。
- 【短邊 < 600px】：**不擋**，但以警告提示辨識可能不準，並要求務必檢查辨識結果。
- 【檔案讀取失敗】：`FileReader.onerror` 須有處理，顯示錯誤而非無反應。

### EC06 產品類別未選或選錯

- 【選了明確類別】：依 FR05 對應表改寫法條，違規清單與陳情信同步更新。
- 【其他／無法判定】：沿用後端回傳的食安法，並在介面標示此欄位會決定法源。
- 免費模式的後端永遠回「無法判定」，故此欄位**必定需要使用者手動選擇**，
  UI 標籤須明示「會決定陳情信引用哪一部法規，請務必選對」。

### EC07 關鍵字重疊與死鍵字

- 【新詞包含既有關鍵字】（如既有「治療」再加「治療糖尿病」）：
  同一句會被計為兩筆違規 → 收錄前必須擋下。
- 【新詞為改寫過的說法】：如收「骨頭磨損」但裁處書原文為「骨頭**的一個**磨損」，
  中間隔字即永遠不會觸發 → 必須改收較短且穩定的錨點（「磨損」）。
- 【新詞為法規明文允許的宣稱】（「養顏美容」「淡化細紋」「緊緻毛孔」）：
  會誤判合法廣告 → 一律不得收錄。
- 資料庫維護須提供自動化驗證，於寫入前檢出上述三類問題。

### EC08 剪貼簿權限被拒

- 【頁面有焦點】：複製成功，顯示成功訊息。
- 【頁面失焦或瀏覽器拒絕】：`clipboard.writeText()` 會 reject，
  必須 `.catch()` 並提示改用手動選取 + `Ctrl + C`。
  不得只寫 `.then()`，否則使用者以為複製成功、貼出來是空的。

### EC09 網路不可用

- 【備援 OCR 模型無法下載】：顯示「無法載入辨識元件，請確認可連上網際網路」，
  主引擎與純文字分析不受影響。
- 【Gemini 無法連線／金鑰無效／超過額度】：分別給出可辨識的訊息
  （網路問題／金鑰請重新設定／已超過免費額度請稍後再試），不得只顯示 HTTP 狀態碼。
- 系統核心流程（Windows OCR + 關鍵字比對 + 陳情信）須在**完全離線**下可用。

### EC10 法規資料異常

- 【`regulations.json` 格式錯誤】：程式啟動失敗，須於主控台顯示可讀錯誤。
- 【關鍵字清單為空】：分析結果為 0 項違規，須與「確實無違規」區分呈現。
- 【使用者修改後未重啟】：說明文件須在顯眼處警告「改完必須關掉程式重開，重整網頁沒用」。

## 3. Non-Functional Requirements（非功能性需求）

### NFR-S 資安與隱私

| 編號 | 需求 |
|---|---|
| NFR-S01 | 免費模式全程在本機執行，廣告圖片與檢舉人個資不得離開使用者電腦 |
| NFR-S02 | 檢舉人個資（姓名、電話、Email）僅存在瀏覽器記憶體，不寫入伺服器、不落地儲存 |
| NFR-S03 | API 金鑰不得寫入程式碼或版控。Claude 金鑰置於 `api_key.txt`（需列入 `.gitignore`）；Gemini 金鑰僅存瀏覽器 `localStorage` |
| NFR-S04 | 啟用任何 AI 模式前，必須明確告知使用者圖片將傳送至外部服務，並提醒勿上傳含個資畫面 |
| NFR-S05 | 不得為規避防毒軟體而修改程式行為；`ocr.ps1` 採一次性 CLI 設計而非常駐服務 |
| NFR-S06 | 稽核軌跡：目前無任何操作紀錄。若未來開放多人使用，須補上 actor + 時間 + 來源 IP 的稽核（見 OQ04） |

### NFR-P 效能

| 編號 | 需求 |
|---|---|
| NFR-P01 | Windows OCR 單張處理 ≤ 2 秒（實測約 0.7～1.3 秒） |
| NFR-P02 | 關鍵字比對（338 詞）回應 ≤ 200 ms |
| NFR-P03 | 瀏覽器 OCR 首次使用含模型下載 ≤ 60 秒；模型快取後單張 ≤ 10 秒（實測約 5～6 秒） |
| NFR-P04 | 交叉比對不得阻塞主結果呈現；主結果須在 FR02 主引擎完成後立即顯示 |
| NFR-P05 | 圖片長邊超過 4000px 時先縮小再送辨識，避免記憶體與耗時失控 |

### NFR-A 可用性與可維護性

| 編號 | 需求 |
|---|---|
| NFR-A01 | 核心流程（上傳→辨識→比對→陳情信）須在無網路環境下完整可用 |
| NFR-A02 | 免安裝：使用者雙擊 exe 即可執行，不需安裝 Python、Node 或任何執行環境 |
| NFR-A03 | **exe 內建伺服器僅服務 `/`、`/index.html`、`/api/status`、`/api/analyze`，其餘路徑一律 404**。故所有前端資源（CSS、JS、logo、favicon）必須內嵌為單一 HTML 或 data URI，外部資源只能走 CDN |
| NFR-A04 | 前端原始碼須拆檔維護並提供建置腳本，不得直接編輯產出的 `static/index.html` |
| NFR-A05 | 法規與關鍵字資料與程式分離（`regulations.json`），非工程人員可自行增修 |
| NFR-A06 | 支援 Chromium 核心瀏覽器（Chrome / Edge）最新兩個版本 |
| NFR-A07 | 介面採深色主題，設計語言參考 `設計素材/visual.png`；陳情信列印輸出必須為白底黑字 |
| NFR-A08 | 每次交付須附測試基線數字（單元 / E2E / 誤判 / 召回），寫入版本紀錄 |

## 4. Acceptance Criteria（驗收標準）

> 每條 AC 對應一個可執行的測試或一段人工操作。
> 實作時將 AC 編號寫進測試名稱，供 gap analysis 對照。

### AC01 三種輸入方式皆可觸發分析
- 測試一：以檔案選擇器上傳測試圖 → 預覽顯示、上傳區出現檔名／尺寸／容量。
- 測試二：拖曳圖片至上傳區 → 同上。
- 測試三：焦點在頁面時按 `Ctrl + V` 貼上剪貼簿圖片 → 同上。
- 測試四：不上傳圖片，於文字框貼上「本膠囊可以根治高血壓」→ 可正常分析出違規。

### AC02 主引擎路徑正確且效能達標
- 上傳 `測試資料/違法1_保健食品_醫療效能.png` → 按「開始快篩分析」。
- 預期：狀態列出現「已由 Windows 內建 OCR 辨識出 N 個字」，
  自結果卡片顯示起算 ≤ 2 秒，且辨識文字回填至文字框。

### AC03 三張違法測試圖命中數達標
- 違法1 ≥ 5 項、違法2 ≥ 8 項、違法3 ≥ 12 項，風險等級非「無明顯違規」。

### AC04 三張合法測試圖零誤判
- 合法1／2／3 皆為 **0 項違規**，風險等級「無明顯違規」。
- 補充語料：以認定準則附件一／附件二**明文允許**的宣稱詞句組成的 12 組合法文案，
  全部 0 命中（涵蓋「養顏美容」「調整體質」「淡化細紋」「緊緻毛孔」「增加飽足感」等）。

### AC05 真實裁罰案例召回
- 以 18 則主管機關實際裁處案例的**廣告原文**逐則送分析。
- 預期：18 則全部至少命中 1 項違規。
- 涵蓋案例須包含 A.H.A 關捷挺固立（罰 1,124 萬）、Dr.穆拉德芯立強（罰 198 萬）、
  FORTE 再生抗皺面膜（罰 529 萬）、台中龜鹿膠案等。

### AC06 OCR 正規化有效性
- 測試一：`tidyCJK('７天美白')` 結果含 `7天美白`（全形轉半形）。
- 測試二：帶字間空白的 OCR 原文（`超 級 美 白 丸 7 天 美 白…`）經處理後，
  關鍵字命中數由 1 提升至 9。
- 測試三：`tidyCJK('BUY NOW 立 即 購 買')` 仍保留 `BUY NOW` 的空白。

### AC07 引擎降級與交叉比對
- 測試一（降級）：暫時移除 `ocr.ps1` → 上傳圖片並分析 →
  自動改用瀏覽器 OCR，仍抓到 ≥ 4 項違規，主控台零錯誤。
- 測試二（交叉比對）：上傳違法1 → 主引擎得 5 項 →
  背景交叉比對完成後違規數增為 6 項，並顯示「又補抓到 N 項」提示。

### AC08 使用者修正不被覆蓋
- 分析違法3 得 12 項 → 將文字框內容整段換成「本產品可治療糖尿病」→ 再次分析。
- 預期：文字框內容維持使用者輸入，命中僅 1 項（治療），不得被 OCR 結果覆蓋。

### AC09 法條依產品類別切換
- 測試一：分析違法2（化粧品）→ 預設引用《食品安全衛生管理法》。
- 測試二：產品類別改選「化粧品」→ 違規清單即時改為《化粧品衛生安全管理法》第10條，
  罰則級距顯示 4萬～20萬（誇大不實）。
- 測試三：生成陳情信 → 8 段引用法條全部為化粧品法，
  且說明五不得出現「檢舉違反食品安全衛生管理法案件獎勵辦法」。
- 測試四：五類產品（食品／健康食品／化粧品／藥品／醫療器材）各自對應到正確法規 id。

### AC10 陳情信完整性
- 填妥欄位後生成 → 信中須包含：受文機關、產品名稱、產品類別、
  每項違規的引用原句與法條與罰則、檢舉人姓名與聯絡方式、民國年陳情日期。
- 產品名稱未手動填寫時，須自動帶入 OCR 第一行（例：「苦瓜胜肽精華膠囊」）。
- 發現日期未手動修改時，須為當天日期，且信中呈現為民國年（例：「民國 115 年 8 月 24 日」），
  不得出現「（未填）」。

### AC11 輸入防呆與訊息呈現
- 測試一：未上傳圖也未輸入文字即按分析 → 頁面內顯示警告訊息，**不得跳出 alert**。
- 測試二：上傳 `.txt` 檔 → 頁面內錯誤訊息說明不支援的格式。
- 測試三：分析進行中 → 按鈕停用、`cursor: not-allowed`、有轉圈圖示、文字為「分析中…」。
- 測試四：視窗失焦時按「複製全文」→ 顯示改用 `Ctrl + C` 的指引，不得靜默失敗。

### AC12 零錯誤與離線可用
- 測試一：完整走完上傳→分析→交叉比對→生成陳情信→複製，
  主控台 **零 JS 錯誤、零資源載入失敗、零 alert**。
- 測試二：中斷網路後重啟程式，以 Windows OCR 完成一次完整流程（交叉比對允許失敗但不得中斷主流程）。

### AC13 資料維護安全性
- 於 `regulations.json` 新增「治療糖尿病」（已有「治療」）→ 維護驗證須擋下並說明會重複計算。
- 於清單新增「美白」→ 須擋下並說明為法規允許之宣稱用語。
- 修改 `regulations.json` 後未重啟程式 → 分析結果不變（確認載入時機符合 FR04 描述）。

### AC14 交付基線
- 每次交付須附下列數字並寫入版本紀錄：前端單元測試、瀏覽器端對端測試、
  合法文案誤判組數、真實案例召回數。
- v5 基線：單元 41 passed、UX 27 passed、E2E 22 passed、誤判 0/12、召回 18/18。

## 5. Open Questions（未決事項）

> 依平台慣例，未決事項不阻塞開發，一律標註決議狀態與過渡方案。

### OQ01 系統架構是否由單機 exe 轉為正式後端服務
- **決議狀態：由執行者決定**。
- 現況：exe 為 PyInstaller 單檔封裝，內建伺服器僅四個端點且無法修改（原始碼不在專案內）。
  這造成 NFR-A03 的內嵌限制，以及法條寫死食安法必須由前端改寫的繞道。
- 專案內已有 `backend/` 模組（`schema.py` / `api_spec.py` / `validators.py` / `fixtures.py`，
  約 1,150 行），其 `ProductType` 列舉與前端七類完全一致，可作為改寫的契約基礎。
- 過渡方案：維持 exe，前端補償；`backend/` 先以規格與測試夾具形式演進，不接線。
- 切換點：若需多人使用、稽核軌跡或伺服器部署，即應改為正式後端。

### OQ02 陳情信是否需自動送件
- **決議狀態：由執行者決定**。
- 各縣市衛生局線上陳情系統無公開 API，且多需驗證碼。
- 過渡方案：產生列印／PDF 與全文複製，由使用者自行貼至陳情表單。

### OQ03 法規變更的追蹤與更新機制
- **決議狀態：由執行者決定**。
- 現況：法條與關鍵字為靜態 JSON，法規修正後需人工更新，無到期提醒。
- 過渡方案：`說明文件/關鍵字來源.md` 記錄每條的來源與依據日期，便於定期人工複查。
- 建議切換點：若條目數持續成長，應建立年度複查排程或改為線上資料源。

### OQ04 是否需要多人使用與稽核軌跡
- **決議狀態：由執行者決定**。
- 現況為單機單人，無登入、無操作紀錄（NFR-S06 缺口）。
- 過渡方案：維持單機，個資不落地反而降低風險。
- 切換點：一旦部署為共用服務，須同時補齊 RBAC、session 與操作稽核。

### OQ05 AI 模式的資料外流政策
- **決議狀態：由執行者決定**。
- Claude 模式與 Gemini 模式都會把廣告截圖送出本機。
- 過渡方案：預設關閉；啟用前顯示明確告知；免費模式維持完全本機。
- 待確認：組織是否允許將截圖送交外部 AI 服務，以及是否需要保留送出紀錄。

### OQ06 品類擴充範圍
- **決議狀態：由執行者決定**。
- 現有關鍵字集中於食品／保健食品／化粧品；藥品與醫療器材僅有法條對應，缺專屬關鍵字。
- 過渡方案：先以現有五類法條支援，關鍵字依實際檢舉需求逐步補充。
