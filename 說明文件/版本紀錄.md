### 版本可追溯性（重要）

#### v6、v7 的 orphan commit 是什麼

v6 與 v7 原本只有 zip、沒有任何 commit。2026-08-28 把兩個 zip 的內容建成
**orphan commit**（無 parent）並打上 tag，讓 `git checkout v6` 這種操作可用。

刻意做成 orphan、不接到 `main` 的歷史上：

- 這兩個 commit 不是當時做的。接上去會偽造出「當初就有進版控」的假象，
  也會把 `main` 的歷史改掉。做成 orphan 就只是兩個獨立的根，
  `git log main` 看不到它們，只能經由 tag 取得。
- 時間戳分開記：**author** 用 zip 內原始碼檔案的最後修改時間
  （v6 `2026-08-24 15:47:48`、v7 `2026-08-24 16:39:58`），
  **committer** 用 commit 物件實際建立的時間（`2026-08-28`）。
  從物件本身就看得出這是回溯匯入。
- zip 檔本身的 mtime 不能用——v7 與 v8 的 zip 是後來同一時間補打包的。
- 建立後逐檔做 sha256 比對：v6 38 項、v7 48 項，與 zip 完全相符，無缺漏無多出。

匯入前先驗過機敏內容。這兩個 zip 是 `package.py`（v10 才有）出現之前手動打的，
而 `package.py` 正是因為 v8 的 GitHub Release 曾把 `SPEC/課堂練習/` 帶到公開網路
才寫的——所以推到公開 repo 前特別確認過：兩個 zip 都不含課堂練習、金鑰或 `.env`。

> **另註**：`違規廣告快篩.exe` **自 v6 起**從未重建。v6、v7 的 exe 與
> `v8:exe` = `v10:` = `v11:` = `v12:` = `v13:` 位元組完全相同
> （sha256 `8c84a8ee…`，git blob `875597cd0ef6`）。所以：
>
> - 「從 tag 重新建置」對 exe 本身不成立，各 tag 取出的都是同一顆執行檔。
> - 反過來說，把 v6、v7 收進 git 沒有增加任何儲存成本——git 按內容去重，
>   那顆 17 MB 的 blob 早就在庫裡了。
> - 目前功能沒破，是因為 v9 之後的改動全在 exe 外部載入的 `static/index.html`
>   與 `regulations.json`（`ocr.ps1` 同樣自 v8 未動）。這是巧合不是設計保證。

## v19（現行版本）

把純網頁版缺的那段 OCR 補起來。

### 缺了什麼

exe 模式有兩條補讀路徑：`serverOcrVariants` 用不同前處理讓 Windows OCR 再讀
幾趟，再用瀏覽器 tesseract 做跨引擎交叉比對。線上版只有 tesseract 一套，而
`crossCheckWithBrowserOCR()` 第一行就是：

```js
if (standalone) return;   // 純瀏覽器模式本來就只有這一套引擎
```

「只有一套引擎所以不能跨引擎比對」是對的，但**不同前處理再讀幾趟跟引擎數量無關**
——那條路被一起關掉了。結果是線上版讀一次就結束，沒有任何補讀。

### 補上 browserOcrVariants

用跟 exe 模式同一組前處理（2 倍放大／2 倍放大＋對比拉伸）讓 tesseract 再讀，
結果用既有的 `mergeOcrText` 併回去（只併「帶來新關鍵字」的行）。

**先量測才決定要不要做。** 17 張圖跑完：

| 圖片組 | 補讀前 → 後 |
|---|---|
| 六張合成測試圖 | 全部零變化（原圖就讀滿了） |
| 七張真實案例圖 R1–R7 | 全部零變化 |
| **使用者實際丟的廣告2** | **0 → 1**（「不易形成體脂肪」，2 倍放大讀到） |
| **使用者實際丟的廣告3** | **0 → 1**（「漢方」，對比拉伸讀到） |
| 廣告1、廣告4 | 零變化 |

**一張都沒有退步**（沒有任何圖因為補讀而少抓）。

值得注意的是：合成的測試圖補讀完全沒用，有用的全是使用者實際丟進來的真實廣告
截圖——版面雜、對比差、字疊在照片上、還有 logo 與人像干擾。那正是實際使用時
會遇到的那一群，也是測試素材照不到的地方。

代價是每張多約 1.5 秒（最大那張 4.4 秒），所以放在背景、**出結果之後**才跑，
補到新違規才更新畫面。

### 順帶修掉兩個被那行 early return 連帶壓住的缺陷

**一、線上版永遠看不到「辨識不可靠」警語。**
那段警語寫在 `crossCheckWithBrowserOCR()` 尾端，而線上版第一行就 return 了。
線上版正是唯一 100% 依賴瀏覽器 OCR、最需要這個警語的那一版。移到 `finally`，
兩種模式都會發。順便把建議改成「用左鍵框選要看的那一塊單獨辨識」——那是 v18
新增的功能，比叫使用者去用剪取工具實際得多。

**二、背景補讀的轉圈不會停。**
這個函式有多處提早 return（換過圖、使用者中途改了字、沒補到新文字），
以前那些路徑都會把「背景補讀中…」的 spinner 留在畫面上轉，看起來像卡住。
改成進來先記下狀態列內容，`finally` 一律還原。

### 順帶修掉的：放大沒有像素上限

`prepare(img, scale, enhance)` 之前直接照 scale 建 canvas。4000×3000 的原圖
乘 2 就是 9600 萬像素、約 384 MB 的 RGBA，再 `toDataURL` 會產出上百 MB 的
字串——分頁直接 OOM；iOS Safari 更是超過 1670 萬像素就回空白 canvas。

加上 `MAX_CANVAS_PX = 12e6` 的總像素上限。縮小（`scale < 1`）不受影響。
這條同時保護了 `serverOcrVariants`、`browserOcrVariants` 與 v18 的框選辨識。

### 驗證

新增 `tests/test_ocr_passes.py`（25 項）：補讀函式的接線、
`standalone` 不再被第一行擋掉、信心警語確實在 `finally`、狀態列會還原、
像素上限的計算（含大圖被壓下來、縮小不受影響、不會低於 1 倍）、
以及趟數選擇（小圖 2 趟／大圖 1 趟）。

現行基線：**12 支測試檔 / 392 項檢查**，`pytest backend tests -q` 18 passed。

> 這一版只動前端 OCR 後處理，`backend/`、`regulations.json` 與判定邏輯沒有變動。

## v18

三件事：一個新功能、一個使用者回報的 bug、一輪文件補齊。

### 1. 框選辨識

用滑鼠左鍵在預覽圖上拖出一個框，放開就只辨識那一塊，結果接在「廣告文字」
後面自成一行。同一張圖可以重複框，每塊各自一行，重複框到同一塊不會重覆加。

為什麼需要：整張讀常常把頁尾、浮水印、旁邊的留言也讀進來；密集的資訊圖表
更是整片糊掉（R9 那張整體辨識信心只有 44）。框選還有一個附帶好處——裁切
出來的小塊會單獨放大到辨識引擎的舒適區再讀，比在整張圖裡讀同一塊準得多
（實作上放大到約 900px 寬，但受 1200 萬像素上限約束，免得大圖把分頁吃爆）。

框選的結果也會套用幻覺行濾除，辨識途中換圖則整批作廢。

### 2. 換圖後仍沿用舊文字（使用者回報）

> 手動輸入後，若放新的圖需要重新整理，現況是會維持手動輸入的文字內容，
> 不會辨識新的圖片內容。

這是 v14 我自己種下的。當時為了守 L1 規則（機器不覆蓋使用者的字），
換圖時只清機器辨識的結果、保留手打的內容，而且因為欄位非空就不自動分析。

**那條規則在「同一張圖」上是對的，換圖時卻剛好相反**：留著舊文字會讓陳情信
引錄 A 圖的文字、卻附上 B 圖的截圖，送出去只會被承辦人剔除。

改成換圖一律清空並自動分析。手打的內容不是不重要，所以清掉之後給一顆
「還原剛才的文字」按鈕，而不是默默丟掉。還原時會另外提醒那段文字對應的是
上一張圖。（實作細節：還原提示要排在分析之後才貼——`runAnalysis()` 開頭會
`clearNotice('noticeStep1')`，先貼會被立刻清掉；分析若出錯，錯誤訊息優先。）

### 3. OCR 幻覺行：信心相當時改用面積判別

v16 的規則要求「壓制者的信心高出 40 以上」。使用者回報 R6 這張多出一行
「可寺咆合」，查下去是**兩行都 conf 0**，信心差 0，條件不成立所以沒濾掉：

```
conf=0  x=113-288  y=55-77    "可寺咆合"      ← 幻覺，面積 3850
conf=0  x= 61-311  y=55-100   "黑豆玥物飲"    ← 真實標題，面積 11250
```

兩個框 100% 重疊——幻覺是同一塊區域的「子假設」，框一定比較小而且被包在
裡面。所以補一條：信心差在 20 以內時改看面積，對方大 2 倍以上就判它是本尊。

實測 15 張測試圖，這條規則**剛好只多丟掉「可寺咆合」一行**，關鍵字命中
維持 47 一個沒少（面積比門檻 1.5／2.0／2.5 結果都相同）。

### 順帶查了 PSM，結論是不要動

過程中發現 **tesseract.js 的預設不是 PSM 3 而是 PSM 6**，而 PSM 4 能把 R6
的標題正確讀成「黑豆穀物飲」（conf 93，預設模式是 conf 0 的亂碼）。看起來
很誘人，但整批量測後兩條路都不能走：

| 設定 | 平均信心 | 零信心行 | 關鍵字命中 |
|---|---:|---:|---:|
| 現行（PSM 6） | 78.5 | 8 | **47** |
| PSM 4 | 79.9 | 2 | 36 ← 違法3 從 12 個掉到 1 個 |
| PSM 3 | 80.7 | 7 | 45 ← 且濾除會誤刪「延年益壽、青春永凡」整行 |

PSM 4 在「違法3_食品_漢方誇大」會漏掉化痰、止咳、清肺、活血、排毒等 11 個
真實違規詞。PSM 3 表面數字最好，但改變切行方式之後，幻覺濾除開始誤刪真實
內容。**維持現狀**，只補面積判別。

這也修正了 v9 紀錄裡「PSM 三種設定實測完全沒有差異」的說法——那是在單一張
小字圖上量的，換一批圖差異很明顯，只是差在會漏抓。

## v17

解掉一個從 v10 就掛在那裡的已知限制：**領有健康食品許可證的產品被誤判**。

### 問題

「調節血脂」「護肝」「免疫調節」這 13 個詞是衛福部公告的**法定保健功效**。
領有健康食品許可證（健字號）者，得在核准範圍內合法標示；一般食品宣稱才違法。

工具只讀廣告文字、無法查證有沒有領證，所以這 13 項一律標成「疑似・待認定」。
測試資料 `R7_已知限制_領證健康食品.png` 就是為此列的——說明文件寫著
「本工具無法查證有無領證」。

### 作法：建置期快照，不是執行期查詢

食藥署有開放資料（[健康食品資料集](https://data.gov.tw/dataset/6951)，編號 19），
但**沒有走執行期 API**，理由有三個，都是實測出來的：

1. **CORS**：`data.fda.gov.tw` 的回應沒有 `Access-Control-Allow-Origin` 標頭，
   瀏覽器直接 fetch 會被擋掉，線上版根本走不通。
2. **離線承諾**：這個工具的賣點之一是「圖片與檢舉人個資不會離開這台電腦」。
   執行期查外部 API 會把產品名或字號送出去，破壞那個承諾。
3. **成本極低**：精簡後 565 筆只有約 150 KB（gzip 20 KB），內嵌完全划算。

所以新增 `健康食品許可證.json` 快照 + `實作作業/update_healthfood.py` 更新腳本，
由 `build.py` 注入前端，全程離線。

### 比對規則

廣告文字裡找到健字號 → 查快照 → 依證況分三種行為：

| 情況 | 行為 |
|---|---|
| 查到、證況「核可」 | 列出核准的保健功效與**宣稱原文**；核准範圍內的用語**不列為違規、也不寫進陳情信** |
| 查到、證況失效／註銷／廢止／併証 | **不放行任何項**，並提示該證非有效，請主管機關一併查核 |
| 廣告有寫字號但查無 | 只說「本快照查無此字號」並附官方查詢連結 |
| 廣告沒寫字號 | 行為與 v16 相同 |

**兩件刻意不做的事**：

- **不判斷「宣稱有沒有逾越核准範圍」。** 那要語意比對，不是字串比對做得到的。
  面板改成把 TFDA 核准的宣稱原文原封不動列出來，讓人自己對照。
- **查無字號時不寫「未經核准」。** 快照是靜態檔、每週才更新，而且 OCR 也可能
  讀錯字號。措辭一律保守。這跟 v7 修掉的誣告風險是同一類考量。

另外，持證**也不得**宣稱醫療效能（健康食品管理法第14條第2項），
所以只有那 13 項法定保健功效會被排除，「治療糖尿病」這類仍然全部保留。

### 順帶補上的關鍵字

13 項法定保健功效裡，「促進鐵吸收」原本不在關鍵字表（其餘 12 項都在）。
補上後關鍵字 718 → 719，證據等級與其他 12 項一致（`i` 級，來源同一筆）。

## v16

使用者回報：辨識「合法2_食品_穀物飲」時，多出一行圖上根本沒有的
「3繼下台夫愧全」。

### 為什麼會多一行

在暫存區裝了一份 `tesseract.js@5.1.1`（與前端 CDN 同版）直接跑那張圖，
拿到逐行資料後原因很清楚：

```
conf=  0  y= 61- 84  "3 繼 下 台 夫 愧 全"      ← 幻覺
conf= 91  y= 61-111  "台 灣 黑 豆 穀物 飲"      ← 真實標題
```

**tesseract 對同一塊區域產出了兩個互相競爭的行假設**，自己給幻覺那行 0 分，
但 `data.text` 照樣把兩個都串進去。圖片頂端其實是空白漸層，一個字也沒有。

同樣的情形在 `R1_關捷挺固立` 也有一行 conf=0 的「Le朵」，壓在 conf=95 的
「關節保健膠囊」上面。

### 為什麼不能用信心門檻篩

第一個念頭是「砍掉低信心的行」，但把 15 張測試圖全跑過之後，這個做法會出大事：

| 圖片 | 信心 | 內容 | 是否真實 |
|---|---|---|---|
| 合法3_化粧品_防曬 | 7 | `SPF50+PA++++` | **真的在圖上** |
| 違法3_食品_漢方誇大 | 18 | `延年益壽、青春永凡` | **真實違規詞** |
| R2_苦瓜胜肽 | 12 | `苦瓜勝采複方膠囊` | **真實產品名** |
| R3_FORTE面膜 | 44 | `吾噬衰老細胞,修復衰老殘損細胞` | **真實違規詞** |
| 合法2_食品_穀物飲 | 0 | `3繼下台夫愧全` | 幻覺 |
| R1_關捷挺固立 | 0 | `Le朵` | 幻覺 |

低信心的行大多是「讀得很爛但真的存在」的內容。砍掉它們會漏抓違規，
那比多一行亂碼嚴重得多。

### 真正的判別訊號是重疊

幻覺行的共同點不是信心低，而是**它壓在另一個信心高很多的行上面**——
那是同一塊區域的兩個競爭假設。低信心的真實行則都是獨立存在、沒有人跟它搶位置。

規則：某一行同時滿足以下三個條件才丟掉

1. 它與另一行的 **bbox 交集** ≥ 60%（佔較小那個框的比例）
2. 對方的信心比它高 ≥ 40
3. 它自己的信心 < 60

用 bbox 交集而不是只比對 y 範圍很重要——只看 y 的話，雙欄排版會把信心較低
的那一欄整欄誤殺。

### 驗證

15 張測試圖共 88 行，這條規則**剛好只丟掉那 2 行幻覺，其餘一行未動**。
交集門檻 0.4～0.7 × 信心差 30～60 的每一組參數結果都相同，邊界很寬，
所以取中間值 0.6 / 40。

驗證的是**建置產物裡實際出貨的函式**（從 `static/index.html` 抽出來跑），
不是另外寫一份等價實作。除了上面 15 張圖之外還測了邊界：

| 情境 | 結果 |
|---|---|
| 拿不到 `data.lines` → 原樣回傳，不會少讀 | ✓ |
| `lines` 為空、只有一行（即使 conf=0） | ✓ 保留 |
| `null` 輸入 | ✓ 不會爆 |
| 雙欄排版（同 y 不同 x） | ✓ 低信心那欄不被誤殺 |
| 完全重疊 + 信心差大 | ✓ 丟低的、留高的 |
| 信心差只有 30（未達門檻） | ✓ 兩個都留 |

端對端：真實跑 OCR 再套用出貨的濾除，該圖從 **59 字降為 52 字**
（正好是幻覺行的 7 個字），六行真實內容完好。

> 這一版只改瀏覽器 OCR 的後處理，`backend/`、`regulations.json` 與判定邏輯
> 沒有變動。Windows 內建 OCR 那條路徑不受影響（它沒有這個問題）。

### 順帶記錄：這次沒有處理的

同一張圖上「飽足**感**」被讀成「飽足**威**」。那是單字誤認，不是幻覺行，
本版的規則不處理也不該處理——那一行整體信心 78，內容是真的，只是有錯字。
使用者本來就要核對「廣告文字」欄位，介面上的提示也是這樣寫的。

## v15

修 v14 自己造成的問題。使用者回報：分析完之後整個畫面被一層深色遮罩蓋住，
中間寫著「放開就開始分析」，而且不會消失。

### 1. `.hidden` 打不贏 ID 規則

v14 新增的全頁拖曳提示層是這樣寫的：

```css
.hidden{display:none}                      /* 特異度 (0,1,0) */
#dropOverlay{...;display:flex;...}          /* 特異度 (1,0,0) ← 贏 */
```

ID 選擇器的特異度高於 class，所以 `#dropOverlay` 的 `display:flex` 永遠蓋過
`.hidden`。JS 那邊 `classList.toggle('hidden', ...)` 確實有加上 class，
但那個 class 一點作用也沒有——**遮罩從頁面載入的第一秒就一直蓋在畫面上**。

之所以能被截圖下來就是證據：原生拖曳進行中很難截圖，能截到代表拖曳早就結束了。

順著這條線把整份樣式表裡所有會被 `.hidden` 控制的元素都掃過一遍，
發現同一類問題還有一個既有的：

```css
.hidden{display:none}                      /* 第 113 行 */
.ocrbar{display:flex;...}                   /* 第 127 行 ← 同特異度、後定義，贏 */
```

`<div class="ocrbar hidden" id="ocrBar">` 因此在還沒選圖片時就顯示著「—」。

修法是讓 `.hidden` 具備一個「唯一隱藏開關」該有的強度：

```css
.hidden{display:none!important}
```

列印不受影響，這點特別驗過：`@media print` 本來就用 ID 特異度 + `!important`
（`#previewCard`、`#printAttach` 都是 `display:block!important`），
(1,0,0) 仍然贏過 `.hidden` 的 (0,1,0)。

`build.py` 加了一道防呆：`.hidden` 少了 `!important` 就建置失敗。這個坑踩過兩次，
不想再踩第三次。

### 2. 遮罩改成不遮擋內容

原本是 82% 不透明的深色罩加上大方框，整頁幾乎全黑。改成 28% 淡色罩 + 內縮的
細框，中間只留一顆小膠囊提示，頁面內容維持看得見——使用者要看得到自己丟在哪裡。

### 3. 加保險絲，計數器對不齊也不能卡住

`.hidden` 修好之後遮罩就會正常隱藏了，但進出計數本身仍有不保證的情況：
拖曳中按 Esc 取消、把檔案拖出視窗外才放開、或瀏覽器漏發 `dragleave`，
都可能讓計數停在非零。

原生拖曳進行中不會有滑鼠與鍵盤事件，所以只要收到其中任何一個，就代表拖曳
早就結束了：`dragend` / `mousemove` / `pointerdown` / `keydown` / `blur`
任一發生就強制收掉遮罩。已隱藏時直接 return，不會讓頻繁的 `mousemove` 造成負擔。

### 驗證

**層疊結果用程式算過，不是用講的。** 從建置產物 `static/index.html` 解析
`<style>`，做括號感知的規則解析、算特異度與 `!important`，模擬層疊：

| 情境 | 勝出規則 | 結果 |
|---|---|---|
| 螢幕上 `#dropOverlay.hidden` | `.hidden !important` | `none` ✓（原本敗給 `#dropOverlay`→`flex`） |
| 螢幕上 `#ocrBar.ocrbar.hidden` | `.hidden !important` | `none` ✓（原本敗給 `.ocrbar`→`flex`） |
| 螢幕上 `#resultCard.card.hidden` | `.hidden !important` | `none` ✓ |
| 螢幕上 `#letterCard.card.hidden` | `.hidden !important` | `none` ✓ |
| 列印時 `#previewCard.card.hidden` | `#previewCard !important` | `block` ✓ |
| 列印時 `#printAttach.hidden` | `#printAttach !important` | `block` ✓ |

拖曳接線與保險絲：從建置產物抽出實際程式碼配最小 DOM stub 跑，22 項全過，
含「模擬 Esc 取消造成卡住 → 五種保險絲各自都能收掉」與
「500 次 mousemove 在已隱藏時零 class 操作」。

`build.py` 防呆反向測過：拿掉 `!important` → 建置 exit 1。

其餘：`pytest backend tests -q` 14 passed、`static` 與 `docs` md5 一致、
內嵌 JS `node --check` 通過、無外部資源引用。

> 這一版只動 CSS 與拖曳的保險絲，`backend/`、`regulations.json` 與判定邏輯沒有變動。

## v14

使用者回報：「拖曳一張圖片分析後，無法拖曳第二張圖片接著分析。」
查下去發現是兩個獨立的問題疊在一起。

### 1. 第二張圖丟出去，整頁狀態就沒了

拖曳事件原本只綁在 `#drop` 上：

```js
drop.ondrop = e => { e.preventDefault(); ... }
```

第一張分析完之後，Step 2～4 的卡片會把 `#drop` 擠到畫面外，而且 `#drop` 自己
也縮成一行字（見下面第 3 點）。使用者要換圖時，幾乎一定是把圖丟在結果區——
那裡沒有任何 handler，於是走瀏覽器預設行為：**直接導航到那張圖片**。

整頁狀態連同已經填好的檢舉人姓名、聯絡方式、發現日期一起消失。看起來就像
「拖曳沒有反應」或「網頁怪怪的」，實際上是整頁被換掉了。

修法是把 dragenter / dragover / dragleave / drop 都收到 `window` 上，
無論丟在哪裡都由我們處理。`dragover` 的 `preventDefault()` 不能省——
少了它，`drop` 事件根本不會觸發。

同時加一層全頁提示（`#dropOverlay`），拖檔案進視窗時顯示「放開就開始分析」，
讓使用者知道不必瞄準那個框。進出用計數器判斷，否則游標經過子元素時
瀏覽器會連發 enter/leave 造成閃爍。純文字拖曳不會跳提示。

### 2. 就算丟對地方，也只是載入而已

舊行為是載入圖片後顯示「按『開始快篩分析』」，使用者得再捲回去按一次。
現在載入完成就直接跑分析，三個入口（拖曳／Ctrl+V／點選檔案）都一樣。

**但有一個情況刻意不自動跑**：「廣告文字」欄位有字、而且不是機器填的。

那代表使用者自己打過或改過字。依 L1 規則（機器不覆蓋使用者的字），
換圖時的清空邏輯不會動它；`analyzeFree()` 又是「欄位有字就跳過 OCR」，
所以自動分析會拿**上一張圖的文字**去配**這一張圖**，產出的陳情信是錯的——
引錄的廣告原文跟附上的截圖對不起來，送出去只會被承辦人剔除。

這種情況改成載入圖片、但不分析，並明講為什麼、以及兩條路各要怎麼做。

### 3. 順手修掉的兩個小問題

- `drop.innerHTML` 原本被整塊覆寫，第一次上傳後「支援哪些格式、單張上限、

## v13

這一版沒有新功能，全部是缺陷修正。起因是全面盤點程式與資料，找出四個會讓
產出的陳情信失去效力、或讓個資防護形同虛設的問題。

### 1. 陳情信的「廣告原文」印的是錯的字

`_normalize()` 把空白刪掉（不是等長替換），但 `_find_original_quote()` 拿
正規化後的索引去切原始字串。Windows OCR 對中文一定會插空白，所以這條在
exe 路徑上是常態觸發：

| 輸入 | 舊的 quote | reason 寫的關鍵字 |
|---|---|---|
| `本 產品 可以 治療 糖尿病` | `可以` | 治療 |
| 同上 | `治療` | 糖尿病 |
| `苦瓜胜肽 精華膠囊 有效 改善糖尿病` | `改善` | 糖尿病 |

quote 位移了「關鍵字前的空白數」。傷害有三層：

1. 陳情信印出的廣告原文是錯的字，承辦人比對不到原廣告，整份檢舉會被剔除。
2. 前端以 quote 為鍵查 `KEYWORD_SCOPE` 與 `KEYWORD_EVIDENCE`。quote 一亂，
   **品類過濾整個失效**（跨品類誤判全數放行）、**證據等級全部 fallback 成
   `i` 級**且來源印空白——v10 好不容易建立的證據分級在 exe 路徑上等於沒有。
3. `dedupeNested` 也以 quote 比對，同樣失效。

改成 `quote = kw`（前端 `analyzeLocal()` 本來就是這樣寫的），並刪掉整個
`_find_original_quote()`。順帶記錄：該函式的前後文擴展是死碼——`start` 初值
即為 `idx` 而 `pos + 1 <= idx` 恆成立、`end` 同理永不縮小，docstring 承諾的
「含關鍵字的最短句子片段」從未實現過。這個死碼反而是 exe 路徑沒有更早爆掉
的原因（quote 至少沒有擴展成整句）。

驗證：帶空白的 OCR 文字，5 項違規全部對得上 `keyword_evidence` 與
`keyword_scope`，0 項查不到表。

### 2. 檢舉人姓名與電話從來沒有被遮蔽

`_SENSITIVE_FIELDS` 存的是大小寫混合的 `"fName"` / `"fContact"`，查找卻用
`k.lower()`，所以這兩個欄位永遠比對不到：

```
輸入 {'fName':'王小明','fContact':'0912345678','complainant_name':'王小明'}
舊的 {'fName':'王小明','fContact':'0912345678','complainant_name':'[REDACTED]'}
```

而 `fName` / `fContact` 正是前端真實的欄位名（`tests/test_e2e.py` 的
`_REQUIRED_IDS` 就列了）。`complainant_name` 那組是對的，剛好掩蓋了問題。
set 內全部改小寫。

### 3. 品類過濾與巢狀去重的順序顛倒，確定漏抓 10 組

`splitByScope()` 先 `dedupeNested()`（砍掉被長詞包含的短詞）再 `applicable()`
（砍掉不適用品類的詞）。當「短詞通用、長詞品類專屬」時，兩步各砍一個，結果
0 命中。

例：食品廣告寫「三週消除橘皮組織」，選「食品」後結果是 0 項違規——長詞
`消除橘皮組織` 是化粧品專屬被 `applicable()` 濾掉，通用短詞 `橘皮組織`
早在 `dedupeNested()` 就被當成已被長詞涵蓋而刪除。

確定漏抓清單：

| 產品類別 | 漏抓的短詞（對應的化粧品專屬長詞） |
|---|---|
| 食品／健康食品 | 橘皮組織、法令紋、魚尾紋、表情紋、受損肌膚、肌膚鬆弛、孕斑、褐斑 |
| 化粧品 | 糖尿病（對應 `根除糖尿病`） |

改成先 `applicable()` 再 `dedupeNested()`，`drop` 也一併去重。順手把同一次
`renderResult()` 裡重複算兩遍的 `splitByScope()` 併成一次。

### 4. 新增語境排除：法定警語不該被判成違規

盤點時找到一批會誤判的關鍵字。原本打算直接拔掉，量測後推翻：

| 裸詞 | 已有的組合詞數 | 證據等級／來源 |
|---|---|---|
| 糖尿病 | 1（`根除糖尿病`） | c 新北市衛生局114年排行第4名 |
| 高血壓／高血脂／咳嗽／氣喘／痔瘡／打鼾／偏頭痛／乳糖不耐症／心律不整 | 0 | c 或 o |
| 殺菌／再生／磨損 | 0 | o 認定基準例示、c 龜鹿膠案 |
| 雷射 | 0 | o 化粧品認定準則附件四 |
| 療程 | 0 | o 化粧品認定準則第5條第2款 |

**拔掉裸詞等於放棄整個病名的召回**（組合詞列舉不完），而 `雷射`、`療程`
是主管機關明文例示的詞，更不該刪。所以改成保留全部關鍵字，只在已知良性
語境抑制，規則寫在 `regulations.json` 的 `context_exclusions`。

誤判的實例（都會被寫成「同類用語業經主管機關實際裁處」）：

```
糖尿病患者、孕婦及嬰幼兒食用前請諮詢醫師。      ← 法定警語，部分還是主管機關要求加註的
高血壓、高血脂患者請依醫囑控制飲食。
本產品經135℃超高溫殺菌，無菌充填，開封前無需冷藏。 ← 食品加工製程標準敘述
外盒採用100%再生紙材。                        ← 包材
本器材採不鏽鋼刀頭，耐磨損不易鈍化。            ← 耐用性
本品外包裝以雷射雕刻防偽標籤。                  ← 印刷工藝
```

兩種排除方式：

- **吸收型（無條件）**——命中只是某個良性長詞的一部分：`再生紙材` 裡的
  「再生」、`耐磨損` 裡的「磨損」、`超高溫殺菌` 裡的「殺菌」。這種情形跟
  句子其他地方寫了什麼無關，直接排除。
- **語境型（三個條件）**——同句要有警語片語、**且**沒有療效動詞、**且**
  沒有其他無法被語境排除的違規命中。

後面兩個條件都是必要的，各自守住一種規避寫法：

```
本品可根治糖尿病，糖尿病患者請諮詢醫師。  → 仍命中（同句另有「根治」）
三個月改善高血壓，請諮詢醫師。            → 仍命中（療效動詞「改善」否決）
糖尿病患者請諮詢醫師。本品可治療糖尿病。  → 仍命中（另一句是乾淨的違規）
```

第三個條件也讓「高血壓、高血脂患者請依醫囑控制飲食」能正確排除——兩個病名
互為彼此的「其他命中」，判斷時要先看對方是否本身就可被排除。

規模：5 條規則 / 14 個關鍵字 / 27 個警語片語 / 31 個療效動詞否決詞。

刻意不收的：
- 否決清單不收「控制」（警語常寫「請依醫囑控制飲食」）與「有效」（「有效期限」）。
- `療程` 與 `存活率` 不納入護欄。前者出自化粧品認定準則附件，化粧品廣告寫
  療程本身就是被例示的違規態樣；後者的排除語境（第三方檢驗報告）太容易被
  業者照抄規避。

`build.py` 加上 `CONTEXT_EXCLUSIONS` 注入，前後端共用同一份規則。

## v12

### 1. OCR：多趟補讀，並在讀不可靠時明講

使用者回報「還是會辨識並打出亂碼」。實測 15 張測試圖後釐清兩件事：

**拉丁亂碼（`RICRASLBRAN` 那種）已經沒有了。** 成因是早期 tesseract 掛
`chi_tra+eng`，英文模型在低解析中文上會搶贏；現在只載 `chi_tra`。
現行失效模式是中文對中文的誤認：拆字（激→冫敫）、形近替換（口→囗、廣→黂）、
掉字（改善→改）。

**主要引擎完全沒有前處理。** 瀏覽器那條路早就依字高自動放大，
`ocr.ps1` 卻直接餵原圖。量測各種前處理的關鍵字命中數：

| | 原圖 | 2x | 2x+對比 |
|---|---|---|---|
| R9 資訊圖表 530×557 | 0 項 | 2 | 2 |
| R8 低解析度 520×96 | 0 項 | **1** | 0 |
| 違法1 960×640 | 5 | 4（變差） | **6** |
| 合法1／合法2 | 0 | 0 | 0 |

小圖放大效益極大、大圖盲目放大反而更糟、對比能救回被吃掉的字但對低解析截圖有害——
沒有單一變體全贏，所以改為多趟取聯集，接在既有的背景交叉比對裡（不影響第一趟速度）。
合法圖在所有變體下都是 0 項，代表前處理不會製造誤判。

### 2. 合併策略：只併「帶來新關鍵字」的行

多趟補讀讓 R9 的命中從 0 提到 3 項，但第一版的合併只去除**完全相同**的行——
每趟的誤認方式都不同，同一句話的多個版本因此全部並列：

```
骨買流失像坐雲需飛車
骨質流宍像坐雲雷飛車
骨質流矢像坐雲飛車
```

R9 的文字框變成 73 行亂碼，使用者根本無法核對。試過「字元重疊過半即視為同一行」，
73→38 行但命中掉到 2 項。最後改為**只併入帶來新關鍵字的行**——
多趟補讀的目的就是補抓漏掉的違規詞，沒帶新詞的行對使用者只是雜訊。

結果：R9 **73 行 → 29 行**、命中回到 3 項；其餘 14 張圖行數全部減少、命中不變。

### 3. 辨識不可靠時主動告知

密集小字圖兩套引擎都讀成亂碼（「食藥署」→「食薪點」、「宏醫」→「訣臨」），
換任何合併策略都救不回來。既然救不回來，就不該把亂碼交給使用者「核對」而不說一聲。

先用「多趟結果的字元重疊度」當訊號，**實測失敗**——亂碼裡也有大量常用字，
R9 是 0.858、清晰圖 0.949，門檻無從設起。改用 tesseract 自評的信心值：

| 圖 | 信心 |
|---|---|
| 清晰廣告圖（違法1／合法1／R1） | 83～86 |
| R8 低解析度小字 | 61 |
| R9 密集亂碼 | 44 |

低於 70 就跳警告，說明信心值、原因，並給三個替代做法
（Win+Shift+S 的「文字動作」、換高解析截圖、直接貼文案），
最後提醒「陳情信會引述這段文字當作違規事證，請務必核對後再送件」。

### 4. 規避手法的正規化

食藥署 115 年指引已明文把諧音、錯別字列為可裁處態樣。新增 `denoise()`：
移除零寬字元（業者會插進「治療」中間閃避比對），統一 OCR 常見雜訊（`丶`→`、`、`囗`→`口`）。

**只收在正常文案中幾乎不可能出現的字元，不做形近字猜測。**
實測「容錯一個字」的模糊比對後放棄——合法的「使**排**便順暢」與違規的
「使**小**便順暢」只差一個字，任何容錯一字的比對都會把法規明文允許的宣稱判成違規。

### 5. 新增藥物品類維度（drug_only）

食藥署《藥品廣告法令及審查原則》第四章的共通性不適當詞句裡，
有一批只在藥物廣告脈絡下才構成違規——「根據報導」「熬夜加班者」「你有這種現象嗎」
是藥物廣告的禁止手法（藉報導宣傳、列舉服用對象、危言聳聽），
食品廣告這樣寫並不當然違規。新增第三個品類維度，這類詞只在藥品／醫材套用。

藥品／醫材本身**維持不過濾**（保守設計）：這兩類本得宣稱療效、違規點在核准與否，
我們無從判斷哪些詞不適用，全部列出讓人工判斷。

外文詞句大多未收——實測比對大小寫敏感（`PM2.5` 命中、`pm2.5` 不命中），
`FDA approved`、`clinically proven` 收了也是死詞；`whitening`／`anti-aging`
對化粧品本為合法；`EMS` 會誤判「EMS 寄送」。只收 CPAP、COPD 這類大小寫穩定的縮寫。

### 1. 修正引用已廢止法源（最嚴重的問題）

約 50 個關鍵字的依據是**衛福部 105 年 9 月 6 日部授食字第 1051607584 號公告**
（化粧品得宣稱詞句例示及不適當宣稱詞句例示）。查證後發現：

承辦人一查就會發現陳情信引用的是廢止法源，整封信的可信度都會受影響。

不能只把出處字串換掉——現行準則的附件是**封閉引用**（第3條第4款明寫「附件一所列」），
所以逐一比對四份附件原文後分流：

| 處置 | 詞數 | 依據 |
|---|---|---|
| 維持法規明文 | 18 | 準則第5條第1款（涉及預防、減輕、診斷或治療疾病、疾病症候群或症狀） |
| 維持法規明文 | 4 | 準則第5條第2款（涉及藥品或醫療器材之效能） |
| **降為疑似** | 28 | 只存在於已廢止清單，現行附件一～四查無 |

降為疑似的包括：漢方、中藥、芳香療法、絕對安全、曬不黑、幹細胞、胎盤素、
拉提、V臉、豐胸相關等。這些詞仍會被抓出來，但陳情信會寫成

### 2. 補齊健康食品罰鍰，並修正藥事法引用層級

健康食品的罰則欄原本寫「依同法第24條規定處罰（罰鍰額度請以主管機關裁處及現行條文為準）」

|---|---|

| 健康食品管理法 §14 II（醫療效能） | 第24條第1項**第2款**，40萬～200萬 |

兩者均按次連續處罰至違規廣告停止刊播為止，情節重大者並應廢止健康食品許可證。

### 1. 真實截圖 OCR 品質修正

使用者回報實際廣告截圖辨識出 `RICRASLBRAN « EIAFERSIAXS` 這種拉丁亂碼。
用一張 11pt 小字的模擬截圖跑參數矩陣（語言模型 × 放大倍率 × PSM），找到兩個原因：

| 設定 | 命中 | 拉丁亂碼 |
|---|---|---|
| `chi_tra+eng` @1x（修正前） | 3/6 | **10 字** |
| `chi_tra` @1x | 3/6 | 0 |
| **`chi_tra` @2x（修正後）** | **5/6** | **0** |
| `chi_tra` @3x | 4/6 | 0 |

**原因一：語言模型。** `eng` 在低解析度中文上會搶贏 `chi_tra`，把中文行整段輸出成拉丁亂碼。
改為只用 `chi_tra`——它本身含拉丁字元，SPF50、PA++++ 這類英數仍讀得到（實測 2/2）。
順帶把首次下載量從約 9 MB 降到約 6 MB。

**原因二：放大時機。** 舊規則只在「辨識字數<10 且短邊<1000」才放大，
真實截圖有讀到字（雖然是錯的）就不會放大，卡在最差的 1x。
改為**依實際量到的字高決定**：先辨識一次，從行框取中位數字高，
推算把字高拉到 34px（tesseract 對 CJK 的舒適區）所需的整數倍率。

倍率必須取整數——實測 2.5x 的重取樣雜訊反而讓命中掉回 3/6。
PSM（頁面分割模式）三種設定實測完全沒有差異，不是可用的調校點。

實際 UI 驗證：拉丁亂碼 0 字、正確詞命中 4/6、耗時 2.1 秒。
大字圖（字高 33–34px）維持 1x 不放大，無退步。

另外，量到字高 < 13px 時會主動提示使用者如何取得更好的來源圖。

## v7

本版來自兩份獨立驗收報告的發現。**含一個阻斷級缺陷修正，建議立即更新。**

### 1. 阻斷級：連續處理第二則廣告會產出內容錯誤的陳情信

**問題**：不重整頁面連續處理多則廣告時，第二則之後會沿用**上一則的違規內容與產品名稱**，
畫面上的截圖卻是新的。實測上傳一張完全合法的保濕精華廣告，系統報 6 項違規，
並生成一封指控它「根除糖尿病、不用再打胰島素」的陳情信。

**根因**：換圖時的清空條件是「文字框內容 == 上次 OCR 結果」，但背景交叉比對會把兩套引擎的
結果**串接**起來，而記錄的只有瀏覽器那半段，兩者永遠不相等 → 殘留文字被誤判成使用者手打的字而保留。
交叉比對是每次分析都會跑的，所以這條路幾乎必踩。

**修法**：改用「這段文字是不是機器產生的」旗標，不再用字串比對；換圖時一併重置分析結果、
產品名稱與三張結果卡。

同批修掉三個同源的非同步狀態問題：

| 問題 | 修法 |
|---|---|
| 飛行中的交叉比對會蓋掉使用者剛修正的文字 | 寫回前重新確認，並加版本 token 作廢過期結果 |
| 交叉比對更新結果後，已生成的陳情信不會跟著更新 | 信已顯示就一併重新生成 |
| 分析進行中換圖 → 圖文不符 | 分析期間鎖住上傳；結果回來時比對圖片是否仍是送出時那張 |

### 2. 陳情信改為按廣告原句聚合

**問題**：原本 12 個關鍵字就寫成 12 條獨立違規，每條只引兩個字（「化瘀」「活血」），

**修法**：同一句話的命中合併成一條，引用**整句廣告原文**，後面列出命中的個別用語。
實測 8 項違規聚合為 5 段。

- 新增「廣告刊登者／賣場或粉專名稱」欄位（衛生局需要可特定的被檢舉對象）

- **列印時把廣告截圖當附件一起印**（原本信裡寫「檢附1份」，印出來卻沒有）

**3. 產品名稱自動帶入**：以 OCR 第一行為預設值（廣告文案第一行通常就是品名），

### 操作體驗強化

- **錯誤訊息改為頁面內顯示**：不再用 `alert()` 彈窗，改成卡片內的橫幅訊息，

- **按鈕載入中有明確反饋**：停用時變灰、游標變 `not-allowed`、加上轉圈圖示、
  文字改為「分析中…」，並同時鎖住另一顆按鈕避免重複觸發。
- **上傳區即時檢查**：標示支援格式與 10 MB 上限；非圖片檔或過大檔案會擋下並說明原因；
  上傳後顯示檔名、尺寸、容量；解析度低於 600px 會提醒辨識可能不準。

**1. 圖片辨識：雙引擎互補**

- 兩套引擎辨識結果互有長短，可按「用瀏覽器 OCR 再補一次」把兩邊結果合併，抓得更全。
  實測同一張測試圖：Windows OCR 單獨 7 項 → 合併後 10 項。
