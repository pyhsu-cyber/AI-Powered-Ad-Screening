## v8（現行版本）

### 1. 關鍵字加上品類維度

**問題**：化粧品專屬用語（漢方、療程、雷射）會套用到食品廣告上，反之亦然。
一款名叫「本草養生漢方飲」的產品被用「漢方」二字當成誇大不實去檢舉，承辦人員大概率不採，
還會稀釋同一封信裡其他扎實的指控。

**修法**：`regulations.json` 新增 `keyword_scope`，把關鍵字分成三種適用範圍：

| 範圍 | 數量 | 內容 |
|---|---:|---|
| 化粧品專屬 | 83 | 醫美療程與器械（換膚、拉皮、雷射、微晶瓷）、外用成分（胎盤素、幹細胞、漢方、中藥）、皮膚與毛髮結構（重建角質層、活化毛囊）、外觀處置（除皺、除疤、消除眼袋） |
| 食品專屬 | 90 | 中藥補養臟腑（補腎、養肝、清肺、活血化瘀）、食用與代謝（壯陽、解酒、宿便、利尿）、生化指標（降三高、調節血糖）、健康食品13項保健功效 |
| 通用 | 165 | 治療、根治、抗癌、保證有效等兩類都適用的詞 |

過濾規則刻意保守：

- 只有明確選了「食品／健康食品」或「化粧品」才過濾
- **藥品、醫療器材、其他、無法判定一律不過濾**——寧可多列讓人排除，也不要漏抓
- 被排除時會明確告知排除了哪幾個詞與原因，不是靜默丟掉
- 陳情信只列適用的項目

`keyword_scope` 是 `regulations.json` 的新鍵，exe 不會讀它（它只讀 `demo_keywords` 的兩個陣列），
所以與既有程式完全相容。

### 2. build.py 自動注入法規資料，消除長期的漂移風險

先前 `app.js` 裡的 `LAWS` 表是 `regulations.json` 的手抄副本，文件裡一直警告「改法條要記得同步兩邊」。
本版改由 `build.py` 建置時從 `regulations.json` 讀取並注入 `app.js` 的 `@generated-from-regulations` 區塊：

```
python build.py
  已注入 10 條法條、化粧品專屬 83 詞、食品專屬 90 詞
```

法條與品類資料現在只有 `regulations.json` 一個真相來源，不會再漂移。

### 3. backend 改接 index.html

`backend/app.py` 原本優先載入 `static/index_v2.html`，那是 v3 世代的殘檔
（缺依產品類別切換法條、藥品／醫療器材法條、背景交叉比對，`LAWS` 只有 7 條）。
一旦接線就會讓 UI 靜默回退掉 v4／v5 的功能。已改為一律回傳 `index.html`。

全專案掃描確認：現在只有 `index.html` 這一個進入點，無其他殘留引用。

## v7

本版來自兩份獨立驗收報告的發現。**含一個阻斷級缺陷修正，建議立即更新。**

### 1. 阻斷級：連續處理第二則廣告會產出內容錯誤的陳情信

**問題**：不重整頁面連續處理多則廣告時，第二則之後會沿用**上一則的違規內容與產品名稱**，
畫面上的截圖卻是新的。實測上傳一張完全合法的保濕精華廣告，系統報 6 項違規，
並生成一封指控它「根除糖尿病、不用再打胰島素」的陳情信。

**根因**：換圖時的清空條件是「文字框內容 == 上次 OCR 結果」，但背景交叉比對會把兩套引擎的
結果**串接**起來，而記錄的只有瀏覽器那半段，兩者永遠不相等 → 殘留文字被誤判成使用者手打的字而保留。
交叉比對是每次分析都會跑的，所以這條路幾乎必踩。

**修法**：改用「這段文字是不是機器產生的」旗標，不再用字串比對；換圖時一併重置分析結果、
產品名稱與三張結果卡。

同批修掉三個同源的非同步狀態問題：

| 問題 | 修法 |
|---|---|
| 飛行中的交叉比對會蓋掉使用者剛修正的文字 | 寫回前重新確認，並加版本 token 作廢過期結果 |
| 交叉比對更新結果後，已生成的陳情信不會跟著更新 | 信已顯示就一併重新生成 |
| 分析進行中換圖 → 圖文不符 | 分析期間鎖住上傳；結果回來時比對圖片是否仍是送出時那張 |

### 2. 陳情信改為按廣告原句聚合

**問題**：原本 12 個關鍵字就寫成 12 條獨立違規，每條只引兩個字（「化瘀」「活血」），
同一段法條抄 7 遍。承辦人員得自己回原圖找上下文。

**修法**：同一句話的命中合併成一條，引用**整句廣告原文**，後面列出命中的個別用語。
實測 8 項違規聚合為 5 段。

其他信件改進：

- 新增「廣告刊登者／賣場或粉專名稱」欄位（衛生局需要可特定的被檢舉對象）
- 說明二引錄**廣告全文**（網址失效時仍可佐證）
- **列印時把廣告截圖當附件一起印**（原本信裡寫「檢附1份」，印出來卻沒有）
- 列印改用 `display:none`，不再多印 2～3 頁空白
- 必填檢核：姓名、聯絡方式、日期、網址或平台缺一不可，不再讓「（姓名）」「（未填）」被印出去
- 產品類別仍為「無法判定／其他」時，按生成信會先跳警告要求確認
- 藥品／醫療器材的違規理由改寫，不再出現「非藥物不得宣稱」配「廣告未經核准」的矛盾

## v5

### 1. 產品類別的法條對應從 3 類補到 5 類

v4 只有食品、健康食品、化粧品有對應法規，選「藥品」或「醫療器材」會退回後端預設的食安法。
本版新增三條法規並補上對應：

| 產品類別 | 宣稱醫療效能 | 誇大不實 |
|---|---|---|
| 食品 | 食安法 28-2 | 食安法 28-1 |
| 健康食品 | 健康食品管理法 14-2 | 健康食品管理法 14-1 |
| 化粧品 | 化粧品衛生安全管理法 10-2 | 化粧品衛生安全管理法 10-1 |
| **藥品** | **藥事法 66**（20萬～500萬） | **藥事法 66** |
| **醫療器材** | **醫療器材管理法 41-1**（20萬～500萬） | **醫療器材管理法 41-1** |

藥品與醫療器材本來就得宣稱療效，違規點在於「廣告未經核准或逾越核准範圍」，
所以兩類都對應廣告核准條文，而非療效禁止條文。

另新增備用法條供 AI 模式引用：
- `md-46` 醫療器材管理法第46條（非醫療器材不得為醫療效能之標示或宣傳），罰 60萬～2,500萬
- `pha-69` 罰則從含糊描述補為明確級距：依第91條第2項，60萬～2,500萬

法條內容取自全國法規資料庫現行條文。

### 2. 修掉「比對不到的死鍵字」，真實案例召回補到 18/18

台中龜鹿膠案（食安處查獲，食品與化粧品違規廣告共罰 855.9 萬元）先前**整段 0 命中**，
原因是研究時收的是改寫過的說法：

| 原本收的 | 裁處書實際文字 | 結果 |
|---|---|---|
| `骨頭磨損` | 骨頭**的一個**磨損 | 中間隔了字，永遠比對不到 |
| `膝蓋不會痛` | 膝蓋骨完全就**不會有痛**的感覺 | 同上 |

改收較短、穩定的錨點後，該案從 0 項變成 3 項：

- 移除：`骨頭磨損`、`膝蓋不會痛`（死鍵字）
- 新增：`磨損`、`不會有痛`、`關節痛`、`膝蓋痛`、`痠痛`（醫療效能）、`宿便`、`廢物堆積`（誇大不實）

關鍵字合計 333 → **338**。真實裁罰案例召回 **17/18 → 18/18**，合法文案仍維持 0 誤判。

**維護提醒**：新增關鍵字時請一律用**裁處書原文**去測，不要用自己改寫的句子，
否則會收進一堆永遠不會觸發的死鍵字。

## v4

本版修正驗收測試找到的問題，並強化操作體驗。

### 重大修正

**1. 陳情信不再引用錯誤法源（法律正確性問題）**

v3 以前，不論廣告是食品還是化粧品，陳情信一律引用《食品安全衛生管理法》第28條——
因為示範模式的後端寫死回傳食安法。化粧品檢舉案送出去會引錯法條、罰則級距也是錯的。

v4 起，Step 3 的「產品類別」會決定引用哪一部法規：

| 產品類別 | 醫療效能 | 誇大不實 |
|---|---|---|
| 食品 | 食安法 28-2（60萬～500萬） | 食安法 28-1（4萬～400萬） |
| 健康食品 | 健康食品管理法 14-2 | 健康食品管理法 14-1 |
| 化粧品 | 化粧品衛生安全管理法 10-2（60萬～500萬） | 化粧品衛生安全管理法 10-1（**4萬～20萬**） |

違規清單與陳情信會即時跟著切換，連第五段的檢舉獎勵辦法名稱也會跟著調整
（化粧品不再誤引「檢舉違反食品安全衛生管理法案件獎勵辦法」）。
**請務必選對產品類別。**

**2. 背景交叉比對，補回單一引擎漏掉的違規**

分析完成後會自動用瀏覽器 OCR 再讀一次，把兩套引擎的結果合併後重新比對，
有新增違規才更新畫面並提示。實測：

| 測試圖 | Windows OCR | 交叉比對後 |
|---|---:|---:|
| 違法1_保健食品 | 5 項 | **6 項** |
| 違法3_食品_漢方 | 12 項 | **13 項** |

補回來的「改善心血管疾病」正是 111 年度十大違規食藥廣告第 2 名
（Dr.穆拉德芯立強PLUS膠囊，累計開罰 198 萬元）的違規原文——
Windows OCR 把「改善」讀成「改」就整條漏掉了。

**3. 產品名稱自動帶入**：以 OCR 第一行為預設值（廣告文案第一行通常就是品名），
可自行修改。先前一律是空白或「（示範模式無法辨識）」。

### 操作體驗強化

- **錯誤訊息改為頁面內顯示**：不再用 `alert()` 彈窗，改成卡片內的橫幅訊息，
  分錯誤／警告／成功三種樣式，可手動關閉，成功訊息會自動淡出。
- **狀態文字更明確**：spinner 改為「步驟 1／2　讀取圖片上的文字…」加副標說明
  目前用哪套引擎、預估多久。
- **按鈕載入中有明確反饋**：停用時變灰、游標變 `not-allowed`、加上轉圈圖示、
  文字改為「分析中…」，並同時鎖住另一顆按鈕避免重複觸發。
- **上傳區即時檢查**：標示支援格式與 10 MB 上限；非圖片檔或過大檔案會擋下並說明原因；
  上傳後顯示檔名、尺寸、容量；解析度低於 600px 會提醒辨識可能不準。
- **複製全文**：補上失敗處理。視窗失焦時瀏覽器會拒絕寫入剪貼簿，
  先前是靜默失敗（使用者以為複製成功、貼出來卻是空的），現在會提示改用 Ctrl + C。

### 前端原始碼拆檔

新增 `實作作業/` 資料夾，前端拆成三個檔案方便維護：

```
實作作業/index.html    頁面結構
實作作業/styles.css    介面樣式
實作作業/app.js        前端邏輯
實作作業/build.py      建置：合併成 ../static/index.html
```

因為 exe 的伺服器只服務單一 HTML（其餘路徑一律 404），
改完原始檔要執行 `python build.py` 產生實際執行的 `static/index.html`。

## v3

### 主要變更

**1. 圖片辨識：雙引擎互補**

| 引擎 | 速度 | 特性 |
|---|---|---|
| Windows 內建 OCR（主要） | 約 1 秒 | 離線、免下載，由 `ocr.ps1` 執行 |
| 瀏覽器 tesseract.js（備援／補充） | 約 5 秒 | 首次需連網下載模型約 9 MB，之後快取 |

- 按「開始快篩分析」預設走 Windows OCR。
- 若 Windows OCR 不可用（缺中文 OCR 語言套件、`ocr.ps1` 被防毒軟體擋下、或使用舊版 exe），
  程式會**自動改用瀏覽器 OCR**，不會整個卡住。
- 兩套引擎辨識結果互有長短，可按「用瀏覽器 OCR 再補一次」把兩邊結果合併，抓得更全。
  實測同一張測試圖：Windows OCR 單獨 7 項 → 合併後 10 項。

**2. 違規關鍵字資料庫：34 → 333 個（+299）**

| 分類 | v2 | v3 |
|---|---:|---:|
| 宣稱醫療效能 `medical_efficacy` | 15 | 165 |
| 誇大不實 `exaggeration` | 19 | 168 |

- 來源為衛福部食藥署認定基準／認定準則附件、化粧品認定準則附件一與附件四、
  衛福部105年公告詞句例示、食藥署115年食品廣告指引，以及各縣市衛生局實際裁處案例。
- 每個關鍵字的法規依據與出處詳見 `說明文件/關鍵字來源.md`。
- 涵蓋範圍從原本的食品類，擴充到化粧品／美白／生髮／塑身／醫美訴求。

**3. 介面改版**
- 改為深色主題（參照 `設計素材/visual.png` 的設計語言）。
- 左上角加入 logo，並內嵌為網頁圖示（favicon）。
- 頂部新增 STEP 1～4 進度指示，隨流程點亮。
- 陳情信預覽改為深色背景上的白紙樣式，列印時自動轉為白底黑字。
- 移除頂部模式橫幅與「進階設定」區塊，版面更精簡。

**4. 其他修正**
- 支援 Ctrl + V 直接貼上截圖。
- OCR 辨識結果會自動填入「廣告文字」欄位，**可自行修正後重新分析**
  （v3 修掉了「重新分析會蓋掉使用者修正」的問題）。
- 陳情信新增「產品名稱」「產品類別」欄位，主旨不再出現「（示範模式無法辨識）」。
- 全形英數字自動轉半形，避免「７天美白」比對不到「7天美白」而漏抓。

### 已知限制
1. 只抓字面用語。隱喻、諧音、暗示（例如以「管路」影射血管）抓不到。
2. 示範模式一律引用食安法第28條；若廣告是化粧品，產出陳情信時請自行改為
   化粧品衛生安全管理法第10條。
3. `regulations.json` 於**程式啟動時載入一次**，改完關鍵字必須關掉程式重開才生效。
